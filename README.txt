# Telecom Performance & Environmental Dataset

## Overview
This dataset captures time-series performance metrics and environmental conditions across multiple cellular towers. It is structured as a relational / RDF-style network graph, mapping physical telecom infrastructure to real-time operational status and contextual data.

## Dataset Structure & Relationships
The data is modeled around three core layers:
1. **Cell Towers (`tower_id`):** The primary physical entities (e.g., Towers 1 through 5).
2. **Observations (`hasObservation`):** Time-stamped records that link each cell tower to its operational metrics at a specific hour. 
3. **Contextual Attributes:** Environmental and performance nodes that observations branch out into, allowing for cross-tower analysis and pattern detection.

## Key Attributes per Observation
Each observation record tracks the following parameters:
* **Temporal:** `timestamp` (Hourly intervals, e.g., `2025-01-29 13:00:00`)
* **Network Traffic:** `users_connected`, `users_band` (Categorized as Low, Medium, or High)
* **Performance Metrics:** 
  * `download_speed` & `upload_speed` (Mbps)
  * `latency` (ms), `latency_band` (Low, Medium, High)
  * `congestion` (Binary flag: 0 for normal, 1 for congested)
* **Environmental Context:** `weather` conditions (Clear, Rain, Snow, Storm)


How query log works:

1. How Query Engines Handle X and Y
When a query log contains symbols like X or Y, the query processor or parser treats them as variables to be matched, rather than exact keys in the database.

For example, when evaluating 1.hasObservation.X.weather."Rain":

Find Tower: The engine looks for Tower 1.

Find Observations: It follows the outgoing hasObservation edges to find all observation IDs connected to Tower 1 (e.g., observation numbers 13, 18, 50, etc.).

Substitute & Filter (X): The variable X temporarily stands in for each of those observation IDs. The engine checks if weather == "Rain" for any of them. If observation 50 has weather "Rain", then X = 50 is a match.
